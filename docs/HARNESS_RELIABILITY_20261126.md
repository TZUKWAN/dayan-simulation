# 建模 Harness 严谨性与实现修复规范

本轮强化原生 DSH 助手、思路/修订/方案提示词、程序编译器和源码审核器的工作要求。按用户要求不运行测试、模型或全链验收；本次交付不代表已经证明自动建模的成功率或科学准确性。

## 数学模型与路线

先定义状态、参数、输入、动作、派生量和观测的单位、初边界、更新依赖与时间顺序，贯通“原要求→机制/方程→输入/状态→推进→观测/场景→可证伪参照”。按需求选择算法；DSL 和程序路线只应用各自专属合同，不用历史模板限制自主建模。

用户硬约束、数学不变量、数值方法检查、随机情境结果和运行后交付分别处理。用户固定的要求保留；设计者期待的正效应、事故数或显著性不成为默认通过条件。实际文献数量、证据层级、情境假设、经验校准和现实外推分别说明。

## 一份权威实现

实际提交的 definition JSON 是权威版本。外部 Python 草稿有修改时，重新读取源码并序列化到 definition.source，再核对最终文件；预检和构建使用相同版本。已经自行实现时沿文件通道提交该实现，不切换到另一份默认生成模型。长源码和复杂参数使用现有 definition_path/arguments_path，保留路径安全边界、原需求和数据绑定。

## 实现与检查量

完整可变状态在宏步间持久化，观察和帧函数只读。同步快照、RK阶段重算、事件和随机增量的真实算法与方案一致。几何所有轴、楼层、开口、障碍和出口在初始化、运动、验证和回放中保持一致；人数变化时重新正确计算行列和分组。

当前值、累计量与时间峰值按各自定义计算；动作意图与物理姿态分开。检查量必须来自实际计算，初始化后永不更新的零、目标常量、同式自减、伪依赖和未调用函数不能证明机制正确。优先使用实际平台归档、调用账本和适用的独立参照，不为凑判据数量发明大量自报指标。

## 逐项修复与阶段职责

否决反馈拆成逐条缺陷与反例，核对本次代码的相关分支、依赖状态、观测、方程、引用和帧。一个编号包含多项时在现有修订字段逐项回应。修复必须进入最终提交的源码，未改代码不重复请求审核；保留有效阶段和原始失败，其他科学要求不丢失。

审核依据当前实际源码和真实接口，指出具体函数、表达式与可重现条件；不沿用已修复的旧错误，不把未来才产生的运行归档、图或报告当成当前方案缺陷。决策时点、批次、API尝试及动作人数分别计数。运行成功和经验有效分别陈述；任何阶段都不能虚构通过。
